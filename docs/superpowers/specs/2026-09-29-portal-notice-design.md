# 信息中心通知栏 — 设计文档

- 日期：2026-09-29
- 状态：待用户终审
- 项目代号：portal-notice（挂在 white1star.github.io 门户）
- 关联仓库：`white1star/white1star.github.io`（门户源）、`KuangYeZIXUN`（办公端与运维文档）

---

## 1. 背景与目标

**现状**：员工在站点右下角提交「意见反馈」，内容经 FormSubmit 直接投递到管理员 QQ 邮箱。管理员收到后**无法回复**——表单没有收联系方式，邮件里也没有员工地址，物理上没有回信通道。

**目标**：给管理员一个**公开发布答复**的出口。管理员把答复写成「通知」，全员在信息中心的铃铛里都能看到，同类问题不必重复反馈、重复回答。

**为什么是公开广播而不是一对一**：公司约 42 人，问题高度重复（"矿价页打不开""为什么锡没更新"）。公开答复一次解决所有人的疑问，管理员也不用维护多轮会话。

## 2. 需求确认（访谈结论）

| 维度 | 结论 |
|---|---|
| 位置 | 信息中心门户页右上角，铃铛按钮 |
| 交互 | 点击展开通知面板，按时间倒序；打开即已读，小红点消失 |
| 已读判定 | 浏览器本地记录（纯静态固有限制，换设备会重新亮起） |
| 内容形态 | 日期 + 标题 + 正文；支持置顶 |
| 发布方式 | 管理员口述给 AI，AI 写入数据 → 生成 → 发布并核验 |
| 技术形态 | 纯静态，无接口、无后端服务、无新进程 |
| 现有反馈 | 保留不动，员工仍可私信管理员 |

## 3. 非目标

- 不做一对一私密会话、追问、多轮对话
- 不做推送（邮件/企业微信/钉钉提醒）
- 不做登录与权限，通知全员公开
- 不做通知编辑界面（由 AI 代写，避免手改 HTML 改坏页面）
- 不改矿_news 站与竞品站现有页面结构

## 4. 总体架构

```
数据源 notices.json（门户仓库内，git 管理）
        │  build_portal.py：读 JSON → 注入 index.html 的数据块
        ▼
门户 index.html（静态，含铃铛 UI + 已读逻辑）
        │
        ├─→ GitHub Pages：white1star.github.io/（推送即自动部署）
        └─→ 服务器镜像：/opt/news/portal/index.html
                由 mirror_portal.py 每日 7/9/11/13 点从 Pages 抓取
                39.96.27.206/ 对外提供
```

**关键决定：通知数据内嵌进 HTML，不在页面运行时 `fetch('notices.json')`。**
原因：`mirror_portal.py` 的 `sync_portal()` **只下载并改写 `index.html` 一个文件**（把其中的 `white1star.github.io/` 替换成 `39.96.27.206/`），不同步任何附属文件。若页面运行时去 `fetch('notices.json')`，服务器上的通知区必然空白。内嵌后两个部署地址表现完全一致，且离线可用。
（同一脚本里的 `mirror_xiangsu()` 是竞品站的另一条同步路径，与门户无关，本次不改动。）

## 5. 组件设计

### 5.1 数据文件 `notices.json`

门户仓库根目录，数组，按时间倒序存放（最新在前）：

```json
[
  {
    "id": "20260929-01",
    "date": "2026-09-29",
    "title": "1#锡 现货已恢复每日更新",
    "body": "长江有色把 1#锡 从列表页下架了，已改用其报价接口，现在每 3 小时更新一次。",
    "pinned": true
  },
  {
    "id": "20260928-01",
    "date": "2026-09-28",
    "title": "服务器 10 月 18 日到期",
    "body": "请各部门在 10 月 10 日前确认续费负责人。",
    "pinned": false
  }
]
```

字段规则：

| 字段 | 必填 | 规则 |
|---|---|---|
| `id` | 是 | 全局唯一，建议 `YYYYMMDD-NN`；用于已读判定，不得重复 |
| `date` | 是 | `YYYY-MM-DD`，展示与排序依据 |
| `title` | 是 | ≤ 40 字 |
| `body` | 是 | ≤ 300 字，纯文本，不接受 HTML（防注入） |
| `pinned` | 否 | 缺省 `false`；置顶项排在倒序列表最前 |

`build_portal.py` 校验：非数组、缺字段、`id` 重复、日期格式错、超长——任一命中即报错退出，**不产出半成品页面**。

### 5.2 注入方式

`index.html` 中放一对注释标记，脚本只替换标记之间的内容：

```html
<!-- NOTICES:BEGIN -->
<script>window.__NOTICES__ = [ ... ];</script>
<!-- NOTICES:END -->
```

页面其余结构由脚本与人工维护，通知更新**只改数据块**，不会误伤布局。

### 5.3 前端交互（写在 `index.html` 内，无外部依赖）

- **铃铛按钮**：右上角，`<button>` + 内联 SVG；`aria-label="通知"`，键盘可达
- **小红点**：`unread` 时显示，绝对定位在按钮右上角，8px 红点 + 轻微阴影
- **面板**：点击按钮展开；点击遮罩、按 `Esc`、再次点击按钮均可关闭
- **列表**：`pinned` 优先，其余按 `date` 倒序；每条显示日期、标题、正文
- **空态**：无通知时显示"暂无通知"
- **移动端**（≤760px）：面板全屏宽度，圆角保留，内容可滚动
- **已读逻辑**：
  - 存储键 `portal_notice_read_id`，值为用户最后打开面板时看到的最新一条 `id`
  - 判定：`localStorage` 中的值 ≠ 最新一条 `id` → 显示红点
  - 打开面板时写入最新 `id` 并立即隐藏红点
  - `localStorage` 不可用（隐私模式等）时**静默降级**：不显示红点，功能其余部分正常，不报错

### 5.4 发布工具 `build_portal.py`

放在门户仓库根目录，`python3 build_portal.py`（办公端也可用 `python build_portal.py` 运行同一脚本）：

1. 读并校验 `notices.json`
2. 读 `index.html`，定位标记，替换数据块
3. 写回 `index.html`
4. 打印通知条数、最新日期，便于人工核对

**注入安全性**：`title`/`body` 经 HTML 转义后写入 `window.__NOTICES__` 的 JSON 字面量（`json.dumps` + 替换 `<` `>` `&`），避免正文中的引号或尖括号破坏脚本语法。校验不通过时**不写文件**，已发布页面保持原样。

幂等：连续跑两次输出完全一致（避免 git 里出现无意义 diff）。

## 6. 数据流

| 步骤 | 执行者 | 动作 | 核验 |
|---|---|---|---|
| 1 | 管理员 | 口述「发个通知：…」 | — |
| 2 | AI | 追加 `notices.json`，跑 `build_portal.py` | 打印的条数/日期与预期一致 |
| 3 | AI | 提交并推送门户仓库 | `git status` 干净 |
| 4 | 自动 | GitHub Pages 部署 | 抓 `white1star.github.io/` 校验 HTML 内含新通知 `id` |
| 5 | AI | 触发服务器镜像同步 | 抓 `39.96.27.206/` 校验同上 |
| 6 | AI | 回报管理员 | 两个地址均已可见 |

步骤 5 平时可等服务器 cron（7/9/11/13 点）自动同步；管理员要求立刻生效时，AI 手动跑一次 `mirror_portal.py`。

## 7. 错误处理

| 情况 | 行为 |
|---|---|
| `notices.json` 不存在 | 视作空数组，页面显示"暂无通知"，不报错 |
| JSON 校验不通过 | `build_portal.py` 报错退出，`index.html` 保持原样（不动已发布内容） |
| 标记注释缺失 | 报错退出，提示先检查页面是否被手工改坏 |
| `localStorage` 不可用 | 静默降级：不显示红点 |
| Pages 部署失败 | AI 停在步骤 4 报错，不执行后续同步，避免服务器与 Pages 不一致 |

## 8. 测试

门户仓库目前是纯静态仓库、没有 Python 测试基建。离线测试放在**办公端 `KuangYeZIXUN` 仓库**（已有 pytest 与 venv），通过相对路径指向门户仓库的工作副本进行验证：`tests/test_portal_notice.py`。

用例：

1. 合法 `notices.json` → 注入成功，HTML 内含全部通知 `id`
2. 连续两次构建 → 文件字节一致（幂等）
3. `id` 重复 / 缺 `title` / `body` 超长 / 日期格式错 → 报错退出且 `index.html` 未被改动
4. `notices.json` 缺失 → 注入空数组，不抛异常
5. 标记注释缺失 → 报错退出
6. 已读逻辑：把红点判定抽成纯函数 `shouldShowDot(storedId, notices)`（随 `build_portal.py` 提供），用 Python 镜像同样的判定规则测「相等/不等/空值」三态；页面 JS 与该函数保持同一规则，注释互相指明
7. 注入内容转义：`body` 中的 `<` `&` `"` 不得破坏 HTML 与 JS 语法（用含尖括号的样例断言输出）

人工核验（发布后）：桌面与手机各打开一次，确认铃铛可点、面板可开可关、红点按预期出现与消失。

## 9. 上线与回滚

**上线**：门户仓库推送即生效（Pages 自动部署），无需改服务器配置；服务器镜像下一次同步后跟上。

**回滚**：`git revert` 门户仓库的提交 → Pages 自动回退 → 手动跑一次服务器镜像同步。回滚后通知区回到上一版，站点其余部分不受影响。

## 10. 已知限制（明确接受）

- **已读状态只存在本机浏览器**：换设备/清缓存后红点重新亮起。对"提醒有更新"这个用途够用，不追求精确的已读统计。
- **通知写入需 AI 代劳**：管理员不能自己点网页发布，换来的是零新增服务与零接口风险。
- **服务器镜像有延迟**：非同步触发时，服务器地址最多滞后约 2 小时（cron 7/9/11/13）。
